- [x] **S3.6** [#39](https://github.com/MFrancis-dev/settle/issues/39) `submit-tx`, `status` · 2026-11-05: submit is an optimisation, so `unreachable`/`server_error` answers 200 `{forwarded:false}` and writes nothing, while a rejected hash stays a 4xx; a NEAR-origin deposit sends `nearSenderAccount` = the payer's own account. The status poll reads 1Click (never the client), applies the same idempotent forward-only write the worker will, and separates `polled:false` + `pollReason` from `paid:false`; a settled attempt given a stale read **throws** rather than mis-reporting. §3.3 derived states covered end-to-end: detected → processing → paid, underpaid, refunded → open, paid-after-cancel, overpaid. 11 + 13 tests.

## Phase 5 — Worker (Nov 8)

- [x] **S5.1** [#50](https://github.com/MFrancis-dev/settle/issues/50) `worker/index.ts` with graceful shutdown · 2026-11-06: `startLoop()` takes an injected `sleep`, so the scheduling is testable without fake timers or real waiting; `stop()` sets a flag **and** wakes the parked interval, then awaits the tick in flight — a shutdown that waited out a 60 s sleep, or that killed a tick mid-write, would leave a payment polled upstream and never recorded. Both loops run on the app's own `ServerDeps` (same 1Click client, same database handle, same clock), so there is no second implementation of any rule. `main()` is guarded by an entrypoint check, so importing the module never spawns a process. Run for real: `pnpm worker` logs the intervals, warns on missing env **names only** (never values), and exits 0 on both SIGTERM and SIGINT after printing "finishing the tick in flight". A tick that throws is logged and the loop continues.
- [x] **S5.2** [#51](https://github.com/MFrancis-dev/settle/issues/51) `pollPayments` (5 s) · one-tick tests with fake deps · 2026-11-06: one tick reads `listLiveAttempts` (every attempt that can still move, across invoices, oldest first, capped at `POLL_BATCH = 50` so a backlog drains instead of bursting at a partner service) and calls `syncAttempt` per row. **The worker and the pay page now share one write** — `lib/server/sync.ts` is called by both `pollPayments` and `GET /api/pay/:publicId/status`, which is what makes §3.4's "the poll *is* the worker's idempotent forward-only update" true by construction instead of by convention; the 13 existing status-route tests pass unchanged against it. A tick never throws: 1Click being down is counted `silent` (no write, so "no signal yet" is never recorded as "not paid"), a stale read that would move an attempt backwards is counted `failed` and logged with the **attempt id only** — no address, no client, no upstream body (S7.10 starts here). 14 tests, each one a real tick against PGlite with an attempt opened through the real quote route and a status fixture the vendor's own verifier accepts.
- [x] **S5.3** [#52](https://github.com/MFrancis-dev/settle/issues/52) `expireQuotes` (60 s) · tests · 2026-11-06: `listExpiredQuoteAttempts` selects `awaiting_deposit` rows past `quote_deadline` (the status *is* the "no deposit" half of the rule), and the tick asks 1Click **one last time** before writing, because `expired` is terminal and absorbs: money that lands in the final seconds would otherwise be recorded as expired and could never be corrected — the next `SUCCESS` read is an illegal transition on a dead row. Late money is recorded forward instead (`lateDeposit`). An unreachable 1Click **defers** to the next tick rather than expiring on a network failure; a 404 does expire, since the service keeps no record of that address and a live row would wedge the invoice under the one-live-attempt rule. The invoice is re-derived after every expiry, so it goes back to `open` and the client can get a fresh address (asserted through the real quote route). Tests advance the harness clock past the quote's own 30-minute NEAR window rather than backdating a row. 9 tests.
- Also fixed while writing the worker: `POST /api/pay/:publicId/submit-tx` moved the attempt to `payment_detected` but left the invoice at `open` until the next poll, so the dashboard and the pay page could disagree for up to 5 s. It now re-derives the invoice from every attempt in the same request (`refreshInvoiceStatus`), pinned by a new route test.
